# Resume guide

Content rules for the resume. Build and QA mechanics live in `resume/AGENTS.md`.
The evidence for these rules is in `profile/sources/advice-digest.md`.

## Content
1. **Strongest project first**, not chronological. Real customers, real
   operations, and real incidents outrank side projects.
2. **Only shipped work.** No 예측/가설/roadmap lines.
3. **PAAR with explicit labels** (문제 / 분석 / 해결 / 교훈, or
   링크 → 목적 → 문제점 → 원인 분석 → 해결 방법 → 레슨 런). Reviewers spend
   about a minute per resume, so readability comes first.
4. **The star project may get two PAAR blocks** (for example, the build plus
   the incident).
5. **Link every claim:** repo, postmortem, merged PR, demo. Reviewers won't go
   looking.
6. **Stack per project, grouped by category** (BE / infra / FE). For BE or infra
   targets, put HTML/CSS/JS last and keep FE detail short.
7. **Fundamentals visible:** a self-study section (courses, books, hand-coded
   repo) placed below Projects and above everything else.
8. **Identity line:** "BE 개발자" with cloud and infrastructure skills stated
   separately. Not "클라우드 인프라 엔지니어" unless the target role is infra;
   tailor per application.
9. **Bilingual strength** tied to engineering value. Write "한·영", not "영·한".
10. **Numbers:** only real ones from the profile. Never placeholders like "N%"
    in a sent resume.
